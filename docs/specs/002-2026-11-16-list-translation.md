# 002: Article list automatic translation

Status: implemented; aggregate local verification complete (2026-11-16).

Contract: [implementation plan](../plans/002-2026-11-16-list-translation.md).

## Goal

When the user opens an article list, non-Chinese titles and list excerpts are
translated to Simplified Chinese automatically, using the existing translation
API configuration. The user can switch between original, Chinese-only and
bilingual presentation. Bilingual presentation follows the existing article
detail bilingual hierarchy: the original text stays primary and the Chinese
translation appears below it, visually de-emphasized. Article body translation
and all existing reading interactions remain unchanged.

## Request source and corrections

The user asked for:

- automatic translation of English titles and list summaries when opening a
  list;
- a manual way to turn translation off;
- Chinese-only and bilingual display modes;
- reuse of the existing translation configuration;
- bilingual styling that matches the existing article detail translation, not
  a newly invented visual system;
- an evaluation of whether the current `settings` table should be replaced by
  a key-value design before adding another preference.

The last two points correct the first proposal and are binding requirements in
this document.

## Existing behavior used as evidence

- Article detail translation already distinguishes `original`, `zh` and
  `bilingual` (`ArticleViewMode`). In bilingual mode, the original title remains
  the primary heading and the translated title is rendered below it at reduced
  size and contrast; original body blocks remain primary and translated blocks
  are appended below them with reduced contrast. See
  [article drawer](../../frontend/src/components/article/article-drawer.tsx)
  and the `.rill-translation-*` styles in
  [index.css](../../frontend/src/index.css).
- The list excerpt is generated by `extractSummary()` from item content for
  display. It is not the AI-generated summary feature.
- The existing translation configuration is the OpenAI-compatible endpoint,
  key and model stored in `settings`; list translation must use the same
  configuration and must not introduce another credential source.
- The `settings` table is upstream design, introduced by the upstream commit
  `c31c14e` (“persist settings in backend”). It was not created by this fork.
  Its typed nullable columns and `id = 1` single-row shape are intentional for
  a single-user application with a small, closed preference set; validation
  lives in the handler so allow-lists can change without rebuilding the table.

## Required behavior

### Modes and persistence

- Add one user preference, `list_translation_mode`, with the closed values
  `original`, `zh` and `bilingual`.
- The UI labels reuse the established article translation vocabulary: original,
  Chinese, bilingual.
- The preference is stored in the backend settings and synchronized across
  devices like the existing preferences. `NULL` continues to mean “the user has
  never chosen a value”.
- The local preference cache must preserve an unset state instead of converting
  that state into an explicit stored mode. The effective mode is derived from
  the stored mode and whether a key is configured; a UI control may display the
  effective mode while the stored value remains unset.
- Effective behavior:
  - a stored mode is honored when present;
  - when no mode was ever chosen and a translation API key is configured, the
    effective mode is `bilingual`;
  - when no translation API key is configured, the effective mode is
    `original`, no translation request is made, and attempting to choose a
    translated mode prompts configuration and leaves the stored mode unchanged;
  - if the key is later cleared, the stored mode is retained but the effective
    mode falls back to `original` until a key is configured again.
- `original` means “do not automatically translate the list”. It is the manual
  off switch.

### Automatic translation trigger

- Translation starts when an article list renders in `zh` or `bilingual` mode
  with a configured API key.
- Only the currently loaded page or pages are eligible. When infinite scrolling
  loads another page, its newly loaded items are translated. The application
  must not translate the entire article history in advance.
- Adding another page to the same list must not cancel translation work already
  in flight for earlier items. New items join the pending work; only a mode
  change, list-scope change, retry or unmount aborts active work.
- Newly observed items caused by a refresh follow the same rule.
- Translation must not block list rendering, scrolling, opening an article,
  changing filters or navigating the list. The original content remains visible
  until a translation arrives.

### Eligibility and source text

- Eligibility is evaluated independently for the title and the list excerpt.
- A field is eligible when it contains Latin letters and no CJK characters.
  Fields containing CJK characters are treated as already Chinese and are not
  sent to the upstream model. This keeps Chinese and mixed Chinese/English
  content unchanged.
- Empty fields are skipped. An item with no eligible field is not sent.
- The translation source for the list excerpt reuses the existing display
  extraction’s HTML cleaning and whitespace normalization. It is a longer
  normalized plain-text excerpt than the 150-character display excerpt
  (up to approximately 400 characters), without a display ellipsis. It must be
  cut at a sentence boundary when one is available, otherwise at a word
  boundary; a raw character slice that can end mid-word is not acceptable.
  Display still uses the existing line clamping.
- Translation must not use the full article body unless the item’s excerpt is
  explicitly part of the list view.

### Presentation

- `original`: current list presentation is unchanged.
- `zh`: a translated field replaces its original field in the existing primary
  style. If a translation is unavailable, the original field is shown.
- `bilingual`:
  - the original title remains first and keeps the current title hierarchy;
  - the Chinese title follows on its own line at reduced size and contrast,
    matching the relationship used by the article detail title;
  - the original excerpt remains first and keeps the current excerpt style;
  - the Chinese excerpt follows on its own line with reduced contrast,
    matching the article detail body-translation relationship;
  - no new color palette, font family or visual language is introduced;
  - if only one of title or excerpt is translated, only that field gains a
    second line;
  - if a translation is pending or failed, only the original field is shown;
    the original must not be duplicated as a secondary line.
- Translated text uses `lang="zh-CN"`. Original text uses `lang="en"` when the
  source is known to be English and otherwise omits the attribute; the existing
  Latin/CJK font settings still apply correctly.
- The bilingual layout may increase row height; it must not truncate the
  original title/excerpt beyond their existing line clamps.

### Loading, failure and control

- The list header contains a translation control in the position indicated by
  the user’s screenshot: to the left of the split “mark all as read” control.
  It exposes original, Chinese and bilingual modes.
- When the effective mode would be translated but no API key is configured, the
  control indicates that configuration is required rather than silently
  pretending translation is active.
- The control shows a translating state while work is in progress and a retry
  action after a recoverable failure.
- A failed request must leave the original content readable. Partial results
  are retained; items that did not translate keep the original.
- Batch success is defined by the `done` event, not by the transport promise
  resolving. If the stream ends without `done`, the batch is incomplete even
  when the HTTP response ended cleanly. Completed items remain translated,
  missing items remain original and become eligible for manual retry.
- An explicit cancellation is not a failure: it must not surface an error or
  mark unfinished items as failed.
- Translation failures are reported once at list level, not once per row, and
  must not enter an automatic retry loop. Failure state belongs to the current
  list scope; switching feed, group, filter, mode or retry clears the previous
  scope's blocked items and failure indicator.
- Switching to `original` stops new work and aborts in-flight list translation
  work; already received translations may remain in the session cache for a
  later switch back.
- Selecting a translated mode without a configured key opens the translation
  settings and does not enable the mode.
- The settings dialog and the list-header control must persist this preference
  through one shared save path, including the same immediate local update,
  rollback on failure and superseded-request handling. They must not implement
  separate PATCH/rollback logic.

### Settings schema decision

Keep the existing single-row, typed-column `settings` table for this feature and
add one nullable `list_translation_mode` column through the next ordered
migration.

This is a deliberate decision, not an oversight:

- the table is upstream design, not fork-specific;
- it has a small, closed set of user preferences;
- typed columns give static Go types and one atomic partial-update statement;
- the current `GET`/`PATCH` contract, `NULL` semantics, validation and
  frontend synchronization remain intact;
- a key-value table or a JSON blob would move type checking and validation into
  application code, require a rewrite of the existing settings paths, and give
  no user-visible benefit for this closed preference set;
- a `note` column is operator metadata, not a substitute for a preference
  model, and is not needed by the application.

A key-value or JSON settings refactor is explicitly a separate work item. It is
not authorized by this feature. Revisit it only if settings become open-ended,
plugin-provided, or numerous enough that typed columns materially harm
maintenance.

## API and cross-component contract

### `POST /api/translations/items`

Authenticated endpoint, streaming `text/event-stream` like the existing
translation and summary endpoints.

Request:

```json
{
  "items": [
    { "item_id": 123, "title": "English title", "summary": "English excerpt" }
  ],
  "force": false
}
```

- `item_id` is a caller correlation key only. It is not required to exist in the
  items table; negative ids used by orphaned starred bookmarks are valid.
  Correlation ids must be unique within a request.
- `title` and `summary` are independently optional, but at least one must be
  non-empty for an item.
- Maximum 50 items per request. The frontend uses smaller batches.
- Titles are limited to 500 characters and excerpts to 2000 characters; the
  server rejects oversized payloads with `400`.
- Before the stream starts, malformed input, oversized input and a missing
  translation API key return the existing JSON error envelope (`400`).
- After the stream starts, upstream failures are delivered as an `error` event;
  the HTTP status has already been committed.

Events:

```text
event: meta
data: {"model":"deepseek-flash","total":10}

event: item
data: {"item_id":123,"translated_title":"...","translated_summary":"...","cached":false}

event: done
data: {"model":"deepseek-flash","translated":8,"cached":2}

event: error
data: {"error":"..."}
```

- Cached items are emitted as `item` events with `cached: true` and do not call
  the upstream model.
- `force: true` bypasses cached entries.
- Entries are keyed by the original title and excerpt content, so unchanged
  content reuses the cache and changed content is translated again.
- The upstream is called with batches of items, not once per row.
- `done` is the only batch-success marker and is emitted only when every
  requested item has an `item` event. A stream that ends without `done` is
  incomplete even if it ended without a transport error; the client retains
  received items and treats missing items as retryable. An upstream failure
  after partial results emits `error`, not `done`.
- The list endpoint reuses the existing translator request/batching/cancel/
  timeout/completeness path, the existing server SSE writer, the existing
  configuration loader and the existing translation cache access. The list
  layer only maps fields to existing segments, maps results back to `item_id`,
  and decides per-item completion and output. It must not introduce a second
  LLM client, batcher or SSE parser.

## Constraints

- Do not change the `/api/items` response envelope, ordering, pagination,
  bookmark metadata, read state or bookmark snapshots.
- Do not mutate item content or store translated text in the `items` table.
- Do not change the existing article detail translation behavior, its cache
  semantics or its view-mode preference.
- Do not add a client-side translation credential path; the API key remains
  server-side.
- Do not add a background job system or persistent queue.
- The migration must be additive and must preserve existing settings rows,
  bookmarks, subscriptions, read state and IDs.
- Existing settings `GET`/`PATCH` partial-update semantics and `NULL` meaning
  must remain intact.
- No new third-party dependency is required.

## Non-goals

- Automatically translating the full article body from the list.
- Translating search results, the sidebar, feed names or bookmarks metadata.
- Pre-translating articles during feed pulling.
- Replacing the `settings` table with a key-value or JSON schema.
- Changing the existing article detail bilingual styles or its manual
  translate/re-translate flow.
- Adding user-selectable target languages beyond Simplified Chinese.

## Acceptance criteria

- With an API key configured and the effective mode `bilingual`, opening any
  article list shows the original title first and a de-emphasized Chinese title
  below it, and the original excerpt first with a de-emphasized Chinese excerpt
  below it; the visual relationship matches the existing article detail
  bilingual presentation.
- Switching to `zh` shows only the Chinese title/excerpt (falling back to the
  original when unavailable). Switching to `original` shows the current list
  unchanged and makes no translation requests.
- The mode survives a page reload and is synchronized through the existing
  settings API.
- English-only items are translated automatically; Chinese-only items produce
  no translation request; mixed fields are left unchanged by the stated
  eligibility rule.
- The excerpt sent for translation uses the existing normalized plain-text
  extraction and ends at a sentence boundary when available, otherwise at a
  word boundary; it is not a raw mid-word character cut.
- Infinite scrolling translates newly loaded items on demand without cancelling
  or re-requesting items that are still translating for the same list.
- A failure in one feed/group/filter does not leave the translation control in
  a failed state after switching to another list; the new scope reports its own
  status.
- In bilingual mode, the translated title and excerpt are both smaller than
  their original counterparts and use lower contrast.
- Reopening a list with unchanged content uses cached translations without an
  upstream call; editing an item’s title or excerpt causes a new translation.
- A failed request leaves every affected row readable in its original form and
  offers a retry; partial results remain translated.
- A stream that ends without `done` is not reported as a successful batch;
  completed items remain translated and missing items are retryable. An explicit
  cancellation is not reported as a failure.
- Changing the preference from either the settings dialog or the list header
  applies immediately, persists through the same path, and rolls back on the
  same failure conditions.
- No API key means no requests, original content, and a configuration prompt
  when a translated mode is selected.
- Read/unread state, starred state, unread undo pins, keyboard navigation and
  list membership are unchanged.
- The existing article detail translation and its bilingual styles are
  unchanged.
- Fresh databases and databases upgraded from the previous migration run
  successfully with the new setting.
- Backend tests, frontend tests, typecheck, lint, i18n completeness and the
  application build pass.
